# codeagent

Консольный coding agent с tool calling. Модель только предлагает вызовы инструментов. Runtime проверяет каждый вызов, исполняет его, сохраняет состояние в SQLite и останавливается, когда нужно решение пользователя. Любой запуск продолжается по `run_id` после перезапуска процесса.

Агентских фреймворков нет: цикл, policy, бюджет, восстановление, планирование и журнал написаны в этом репозитории. Единственная зависимость рантайма: SDK `openai`, через него идут запросы к любому OpenAI-compatible Chat Completions API.

## Установка

Нужны Python 3.11+ и Bash. На Windows используйте WSL.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
```

Настройка модели через переменные окружения (пример в `.env.example`):

```bash
export OPENAI_BASE_URL=http://localhost:11434/v1/
export OPENAI_API_KEY=ollama
export OPENAI_MODEL=qwen3:4b
```

Для локальной Ollama: `ollama pull qwen3:4b`, затем `ollama serve` в отдельном терминале.

## Контрольная задача

```bash
codeagent run "Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты." --mode auto
```

Тот же сценарий с планом и подтверждением каждого действия. Команда `approve` повторяется для каждого действия:

```bash
codeagent run "Исправь расчёт итоговой стоимости заказа..." --plan --mode safe
codeagent plan approve <run_id>
codeagent approve <run_id>
codeagent tasks <run_id>
codeagent diff <run_id>
codeagent rollback <run_id>
```

Без модели и сети запуск воспроизводится флагом `--script`: `ScriptedModel` отдаёт заранее записанные ответы, весь остальной runtime работает так же, как с настоящей моделью.

```bash
codeagent run "Исправь расчёт итоговой стоимости заказа" --plan --script examples/fix_order_plan.json
codeagent run "Исправь расчёт итоговой стоимости заказа" --mode auto --script examples/fix_order.json
```

Демо меняет `workspace/order.py`. Вернуть контрольный проект в исходное состояние можно командой `codeagent rollback <run_id>`.

## Команды

| Команда | Что делает |
|---|---|
| `codeagent run TASK [--plan] [--mode safe\|auto] [--workspace DIR] [--policy FILE] [--script FILE]` | создаёт запуск и ведёт его до первой паузы или конца |
| `codeagent status RUN_ID` | статус, задачи, бюджет и ожидаемое решение |
| `codeagent approve RUN_ID` | разрешить действие, на котором стоит запуск |
| `codeagent deny RUN_ID --reason TEXT` | отклонить действие; причина уходит модели |
| `codeagent plan show\|approve\|reject RUN_ID [--reason TEXT]` | показать, утвердить или отклонить план |
| `codeagent resume RUN_ID` | продолжить после падения процесса или конфликта |
| `codeagent resolve RUN_ID retry\|fail\|abort [--adopt\|--disown]` | решить судьбу вызова, прерванного сбоем |
| `codeagent tasks RUN_ID` | чеклист задач и подтверждения их результата |
| `codeagent diff RUN_ID` | изменения файлов, сделанные запуском |
| `codeagent rollback RUN_ID` | откатить изменения запуска |

Глобальный флаг `--state DIR` ставится перед командой и задаёт каталог с базой запусков, по умолчанию `.codeagent`. Он должен лежать вне workspace.

## Инструменты

| Инструмент | Аргументы | Эффект | Повтор после сбоя |
|---|---|---|---|
| `list_files` | `path` | чтение | да |
| `read_file` | `path` | чтение | да |
| `write_file` | `path`, `content` | запись | да |
| `delete_file` | `path` | удаление | да |
| `bash` | `command`, `cwd` | исполнение | нет |
| `submit_plan` | структура плана | только в Plan Mode | не требуется |
| `complete_task` | `task_id`, `summary` | только при исполнении плана | не требуется |

Каждый инструмент передаётся модели с именем, описанием и JSON Schema. Перед исполнением runtime проверяет имя и аргументы по схеме. Результат возвращается сообщением `role: tool` с исходным `tool_call_id` в виде JSON: `{"ok": true, ...}` или `{"ok": false, "error": "..."}`. Ошибка инструмента не останавливает цикл, модель читает причину и выбирает следующий шаг.

`bash` возвращает `stdout`, `stderr` и `exit_code`. Процесс запускается в отдельной группе с таймаутом и минимальным окружением: `PATH`, `HOME` (указывает на workspace), `LANG`, `PYTHONDONTWRITEBYTECODE=1`. Ключи API в окружение команды не попадают. Вывод пишется во временные файлы, а не в пайпы, поэтому вызов заканчивается вместе с командой, даже если она оставила фоновый процесс. Из файлов читается не больше разрешённого числа байт.

## Policy

Пример лежит в `policy.toml`, вне workspace:

```toml
[commands]
allow = ["python3 -m unittest -v", "python3 -m unittest", "ls", "ls -la"]
deny = ["rm", "bash", "sh", "python3 -c", "git push", "curl"]

[directories]
allow = ["."]
deny = ["private", ".git"]

[limits]
bash_timeout_seconds = 30
tool_output_bytes = 20000

[budget]
model_requests = 40
tool_calls = 80
side_effects = 20
output_bytes = 200000

[journal]
ignore = ["__pycache__", "*.pyc", ".DS_Store"]
```

Правила для команд:

- Команда разрешена, только если совпадает с одной из строк `commands.allow` слово в слово. Лишние пробелы не важны.
- Слова могут состоять только из `A-Z a-z 0-9 _ @ % + = : , . / -`. Поэтому пайпы, `;`, `&&`, перенаправления, `$(...)`, обратные кавычки, кавычки и переводы строк отклоняются, и `bash -c '...'` пройти не может.
- Правило `deny` срабатывает, если его слова встречаются в команде подряд в любом месте. `env rm x` попадает под правило `rm`.
- Запрет важнее разрешения. Всё, что не разрешено явно, отклоняется.
- Аргументы, похожие на пути, проходят те же проверки, что и пути файловых инструментов, относительно `cwd`.

Правила для путей и директорий:

- Директории в конфиге задаются относительно workspace и приводятся к каноническому виду. Разрешённые директории обязаны лежать внутри workspace, иначе конфиг не загрузится.
- Путь отклоняется, если он абсолютный, содержит `..` или проходит через симлинк в любой своей части.
- Запрещённая директория запрещает и всё внутри неё, даже если родитель разрешён. Сравнение идёт без учёта регистра и Unicode-нормализации, поэтому на macOS путь `PRIVATE/x` не обходит запрет `private`.
- Файлы из `[journal] ignore` (имена сравниваются без учёта регистра) можно читать, но инструменты записи и удаления их не трогают: журнал их не видит, и откатить такую правку было бы нельзя.

Защита самого policy-файла:

- Policy-файл обязан лежать вне workspace, иначе запуск не стартует. Файловые инструменты до него не дотягиваются.
- При старте запуска текст policy копируется в базу. Запуск до конца работает по этой копии, в том числе после resume, поэтому правка файла не меняет правила уже идущего запуска.
- Разрешённая команда может запустить код, который агент написал сам, например тест. Поэтому runtime запоминает содержимое policy-файла перед каждым действием. Если после действия файл изменился, runtime возвращает прежнее содержимое и останавливает запуск со статусом `failed`.
- После каждого действия runtime проверяет пути, которые оно изменило. Если команда записала файл в запрещённую директорию, запуск останавливается со статусом `failed`, а правку можно откатить.

Режимы:

| Действие | `safe` | `auto` |
|---|---|---|
| чтение | сразу | сразу |
| запись | после подтверждения | сразу, если прошло ограничения |
| Bash | после подтверждения | сразу, если прошло ограничения |
| удаление | после подтверждения | после подтверждения |

Policy не заменяет изоляцию процесса: разрешённая программа работает с правами пользователя. Запускайте агента на учебной копии проекта без секретов.

## Подтверждение действия

Если действие требует подтверждения, runtime помечает вызов как `awaiting_approval`, сохраняет состояние, печатает действие с подсказкой и завершает процесс.

```bash
codeagent approve <run_id>
codeagent deny <run_id> --reason "тесты не трогаем"
```

После `approve` тот же запуск продолжается, а runtime ещё раз проверяет policy непосредственно перед исполнением. После `deny` модель получает результат инструмента `{"ok": false, "error": "the user denied this action: тесты не трогаем"}` и сама выбирает следующий шаг. Все решения пишутся в таблицу `decisions`.

## Plan Mode

Флаг `--plan` запускает работу с фазы планирования. В ней модели предлагаются только `list_files`, `read_file` и `submit_plan`. Если модель всё же вызовет запись, удаление или Bash, policy отклонит вызов, потому что фаза планирования запрещает любой побочный эффект.

План передаётся вызовом `submit_plan`, проверяется по JSON Schema и сохраняется в таблицу `plans` с номером версии:

```json
{
  "goal": "...",
  "steps": [
    {"id": "T1", "description": "...", "tools": ["read_file"], "depends_on": [], "check": {"kind": "read", "target": "order.py"}},
    {"id": "T2", "description": "...", "tools": ["write_file"], "depends_on": ["T1"], "check": {"kind": "changed", "target": "order.py"}},
    {"id": "T3", "description": "...", "tools": ["bash"], "depends_on": ["T2"], "check": {"kind": "command", "target": "python3 -m unittest -v"}}
  ],
  "risks": ["..."],
  "assumptions": ["..."],
  "done_criteria": "..."
}
```

Кроме схемы, runtime проверяет уникальность id шагов, известность инструментов и зависимостей и отсутствие циклов. Неверный план возвращается модели с причиной. Текстовый ответ вместо плана получает одно напоминание, второй завершает запуск со статусом `failed`.

```bash
codeagent plan show <run_id>
codeagent plan approve <run_id>
codeagent plan reject <run_id> --reason "сначала проверь округление"
```

После отклонения модель получает причину и присылает новую версию плана. Утверждение переводит запуск в фазу исполнения, но ничего не разрешает заранее: в `safe` каждое действие по-прежнему ждёт подтверждения.

## Задачи

Шаги утверждённого плана становятся задачами с id, описанием, зависимостями, состоянием (`pending`, `active`, `done`, `failed`) и проверкой. Runtime берёт первую задачу, у которой выполнены все зависимости, и сообщает её модели. Каждый вызов на фазе исполнения сохраняется с `task_id` активной задачи. Вызовы фазы планирования хранятся без `task_id`.

Задача завершается, когда модель вызывает `complete_task`, а runtime находит подтверждение в записанных вызовах этой задачи:

| `check.kind` | Что должно быть записано |
|---|---|
| `read` | успешный `read_file` указанного пути |
| `changed` | изменение файла, зафиксированное журналом |
| `command` | последний запуск команды завершился с кодом 0, и после него файлы не менялись |

Без такого подтверждения `complete_task` возвращает ошибку, текстового заявления модели недостаточно. Ответ на повторный `tool_call_id` подтверждением не считается, потому что команда при этом не исполнялась. Подтверждение (какой вызов его дал) сохраняется в задаче.

Пока задача активна, текстовый ответ модели не заканчивает запуск: runtime один раз напоминает про задачу. Если модель снова отвечает текстом, задача получает статус `failed`, и запуск завершается со статусом `failed`. Когда все задачи выполнены, вызовы инструментов отклоняются, потому что их не к чему привязать, и модель должна дать итоговый ответ.

Чеклист печатается в stdout при каждом изменении состояния задач:

```
- [x] T1 Read order.py to find how the total is computed
- [ ] T2 Rewrite calculate_total ...  <- in progress
- [ ] T3 Run the test suite
```

Проваленная задача помечается `<- failed`. `codeagent tasks <run_id>` показывает чеклист и подтверждения. После resume завершённые задачи не запускаются заново.

## Бюджет

Лимиты задаются в секции `[budget]` и копируются в запуск при создании. Счётчики общие для всех фаз одного `run_id`, и ни resume, ни утверждение плана, ни повтор после сбоя их не обнуляют.

| Счётчик | Когда списывается |
|---|---|
| `model_requests` | перед каждым запросом к модели |
| `tool_calls` | при записи ответа модели, за все вызовы пачки сразу |
| `side_effects` | при старте каждого исполнения записи, удаления или Bash, включая повторы |
| `output_bytes` | при сохранении результата: размер текстового вывода (stdout, stderr, содержимое файла, список файлов) |

Проверка и списание идут в одной транзакции SQLite со сменой состояния действия, поэтому после падения потраченное не возвращается.

Если на всю пачку вызовов не хватает `tool_calls` или `side_effects`, не выполняется ни один вызов из неё. В `side_effects` пачки считаются только вызовы, которые policy пропустила бы прямо сейчас, поэтому запись в Plan Mode бюджет не резервирует.

Инструмент с выводом не стартует при нулевом остатке `output_bytes`. Он получает лимит `min(tool_output_bytes, остаток)` и читает не больше него, а runtime обрезает результат до того же лимита и добавляет поле `truncated`.

Исчерпание любого лимита переводит запуск в статус `exhausted`. Каждый ещё не исполненный вызов пачки при этом получает ответ «not executed».

## Восстановление после сбоя

Всё состояние запуска лежит в `.codeagent/runs.db`: сообщения, вызовы и их попытки, результаты, решения пользователя, бюджет, план, задачи, снимки файлов. База открыта в режиме WAL с `synchronous=FULL`.

Действие с побочным эффектом проходит три шага:

1. Транзакция: списать `side_effects`, сверить и снять снимок workspace, записать попытку со статусом `started`.
2. Исполнить инструмент.
3. Транзакция: снять снимок после действия, сохранить diff, изменения файлов, результат, списать `output_bytes`, добавить сообщение `role: tool`.

Если процесс упал между шагами 2 и 3, при следующем запуске runtime находит попытку `started`. Чтение повторяется автоматически, потому что ничего не меняет. Действие с побочным эффектом становится `uncertain`, и запуск ждёт пользователя. `codeagent resume <run_id>` показывает изменения с начала вызова и доступные решения:

```bash
codeagent resolve <run_id> retry --adopt
codeagent resolve <run_id> fail --disown
codeagent resolve <run_id> abort
```

`retry` повторяет вызов, `fail` считает шаг неуспешным и продолжает запуск, `abort` завершает запуск с ошибкой. Если с начала прерванного вызова файлы изменились, нужно явно выбрать `--adopt` (изменения относятся к запуску и попадают в журнал и откат) или `--disown` (изменения посторонние). Повтор оформляется как новая попытка того же вызова и снова списывает `side_effects`.

Какие инструменты можно повторять:

- `list_files`, `read_file` ничего не меняют.
- `write_file` пишет файл целиком через временный файл и `rename`, поэтому повтор приводит к тому же состоянию.
- `delete_file` удаляет тот же путь, состояние после повтора то же.
- `bash` повторять нельзя: это произвольная программа, и даже разрешённая команда может иметь неповторяемые эффекты.

Повтор `tool_call_id` с тем же именем и аргументами возвращает сохранённый результат без исполнения. Если имя или аргументы отличаются, модель получает ошибку протокола.

Сбой можно воспроизвести: `CODEAGENT_CRASH_AFTER=write_file codeagent run ... --mode auto` убивает процесс сразу после исполнения `write_file`, до сохранения результата. В тестах та же точка отказа задаётся хуком `after_execute`.

## Журнал изменений и откат

Перед каждым действием с побочным эффектом, включая Bash, runtime сравнивает workspace с последним сохранённым снимком. Если файлы изменились снаружи, действие не исполняется, а запуск получает статус `blocked` со списком файлов. После того как файлы возвращены, `codeagent resume` продолжает запуск, и runtime снова сверяет дерево перед действием.

Снимок содержит все пути workspace и SHA-256 содержимого, само содержимое хранится в таблице `blobs`. После действия runtime снимает новый снимок, сохраняет diff попытки и обновляет `file_changes`: хеш до первого изменения файла и хеш после последнего. У созданного файла нет исходного хеша, у удалённого нет итогового.

Секция `[journal] ignore` перечисляет генерируемые файлы, которые не попадают в снимки. Шаблон отклоняется при загрузке, если под него подпадает любой `.py`-файл workspace или любая папка с ним. Поэтому исключения не могут скрыть исходники или тесты.

```bash
codeagent diff <run_id>
codeagent rollback <run_id>
```

Перед откатом runtime проверяет, что нет неразрешённого прерванного вызова, и сверяет текущие хеши с итоговыми. Если хотя бы один файл изменился после последнего действия агента, команда сообщает конфликт и не пишет ни одного файла.

Каждый путь заново проходит проверки policy: он должен лежать внутри workspace, не содержать `..` и не проходить через симлинк. Списки разрешённых и запрещённых директорий к откату не применяются: откат возвращает только то, что запуск уже изменил. Так можно убрать файл, который команда записала в запрещённую директорию.

Откат трогает только файлы из журнала этого запуска и переводит запуск в статус `rolled_back`. Файл, который уже вернулся к исходному состоянию, считается восстановленным, поэтому прерванный сбоем откат можно запустить ещё раз. Вызов, ждавший подтверждения, получает ответ «not executed».

## Статусы запуска

| Статус | Что ждёт |
|---|---|
| `running` | идёт работа или процесс упал; `resume` |
| `awaiting_approval` | `approve` или `deny` |
| `awaiting_plan` | `plan approve` или `plan reject` |
| `uncertain` | `resolve` |
| `blocked` | вернуть файлы и `resume` |
| `completed`, `failed`, `exhausted`, `rolled_back` | конечные |

## Устройство

| Модуль | Ответственность |
|---|---|
| `runtime.py` | цикл агента и решения пользователя: порядок проверок, пауз и записей в хранилище |
| `planner.py` | Plan Mode и задачи: `submit_plan`, `complete_task`, решение по плану, назначение и проверка задач |
| `policy.py` | проверка путей, команд и режима; ничего не знает о цикле |
| `tools.py` | схемы и исполнители инструментов; пути заново проходят через policy |
| `journal.py` | снимки, diff, проверка дрейфа, откат |
| `plan.py` | структура плана, проверка зависимостей, проверка результата задачи |
| `store.py` | SQLite; `atomic()` объединяет несколько операций в одну транзакцию |
| `model.py` | `OpenAIModel` и `ScriptedModel` за одним протоколом `Model` |
| `settings.py` | загрузка и проверка `policy.toml`, защита policy-файла от правок во время действия |
| `cli.py` | команды и вывод |

Runtime спрашивает `Policy.check` о каждом вызове непосредственно перед исполнением, в том числе после подтверждения пользователя и после resume. Исполнители инструментов не доверяют вызывающему коду и снова разрешают пути через policy.
